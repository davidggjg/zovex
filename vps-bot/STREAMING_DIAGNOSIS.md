# אבחון הזרמת VOD — ממצאים מדודים

> נכתב 29/08/2026 אחרי ערב שלם של מדידות. המסמך קיים כדי שלא נחקור
> מחדש דברים שכבר הופרכו. **כל שורה כאן מגובה במדידה, לא בהשערה.**

## התלונה

סרט נטען לאט (לפעמים מעל דקה), ואחרי 10-30 דקות צפייה נכנס ללולאה:
נתקע → המתנה ארוכה → מתנגן כמה שניות → נתקע שוב.

## מה **הופרך** — אל תחזרו לשם

| השערה | הראיה שהפריכה אותה |
|---|---|
| טלגרם מגביל אותנו (FloodWait) | `FloodWait = 0` בשעה שלמה. אף פעם לא הגענו למגבלה. |
| חיבורים מתים | `חיבור מת = 0`. המנגנון קיים ולא מזוהה אף פעם. |
| חסר רוחב פס בשרת | הפאנל: 36 MB/s, תעבורה ללא הגבלה. |
| תקרה של ~8 MB/s | נמדד 9.65 MB/s למשיכה בודדת. המספר הקודם היה סכום של מדידות **טוריות** — לא קיבולת. |
| עומק הקובץ מאט משיכה | "קרוב להתחלה" נמדד **איטי יותר** מ"אמצע". |
| יותר חיבורים לבוט = מהיר יותר | `media_conns=8` נתן 2.46 MB/s מול 7.89 ב-4. **פי 3 גרוע יותר.** |
| צריך עוד בוטים | הבוטים נותנים 4 MB/s כשהם עובדים. הבעיה אינה כמות. |

## מה **אומת**

**1. המערכת מסוגלת להרבה יותר ממה שצריך.**
```
סרט 1.57GB / שעתיים  →  0.22 MB/s נדרש
נמדד אחרי restart     →  2.1 – 9.65 MB/s
```

**2. הזמנים דו-קוטביים — אין "איטי", יש רק "מהיר" או "תקוע".**
```
תקין:  0.4 · 0.6 · 0.8 · 1.0 · 1.7 · 1.9 · 2.4 שניות
תקוע:  44 · 112 · 125 · 132 שניות
```

**3. ההגברה: תקלה של 10 שניות הופכת לתקיעה של 130.**
כשרצועה אחת מאחרת, נזרק כל החלון (כולל רצועות שהצליחו), החלון נמשך
מחדש על בוט אחר ×3, ואז נופלים למסלול ותיק שתולה 25ש' לכל בוט:
```
3 × 9ש'  +  4 × 25ש'  ≈  127ש'      נמדד: 132 · 125 · 112
```

**4. ⚠️ restart מחזיר את המערכת לתקינות מלאה.**
זו התובנה המרכזית. אותה בדיקה בדיוק, 19 דקות הפרש, ההבדל היחיד הוא restart:
```
לפני:  0.03 MB/s (132ש')  ·  0.09 MB/s (44ש')
אחרי:  2.10 MB/s (1.9ש')  ·  9.65 MB/s (0.4ש')
```
**כלומר: הקוד תקין. המערכת מתדרדרת עם הזמן.** חשוד מרכזי —
`MEDIA_SESSION_TTL = 1800` (בדיוק 30 דקות), שמתלבש על "נתקע אחרי חצי שעה".

**5. מטמון הקצה עובד, וההבדל דרמטי.**
```
צפייה ראשונה בסרט:  98 שניות   (הצופה הראשון ממלא את המטמון לכולם)
אותו סרט אחר כך:    1.5 שניות
```

## מלכודות — טעויות אמיתיות שעלו ביוקר

**א. `.env` דורס את ה-drop-ins של systemd.**
`EnvironmentFile=/opt/zovex-bot/.env` נטען אחרון. במשך שעות "כוונַנּו"
דרך `/etc/systemd/system/zovex-bot.service.d/` ושום דבר לא נכנס לתוקף.
**מקום האמת היחיד לפרמטרים: `/opt/zovex-bot/.env`.**
לאמת תמיד: `curl -s "http://127.0.0.1:8000/stream/tune"`

**ב. חימום מטמון ברקע חנק את המערכת.**
`STREAM_EDGE_HEAD=32MB` + חימום כל 5 שניות = **8.8 MB/s משיכה רציפה**,
בזמן שכל הכוח הזמין הוא ~8 MB/s. הסקריפט צרך 110% מהמערכת ולא נשאר
כלום לצופים. **כל תהליך רקע שמושך מטלגרם גוזל ישירות מהצופים.**

**ג. מדידה שנעשית לא נכון גרועה מאי-מדידה.**
- `/speedtest/bots` בודק בוט אחד בכל פעם, **בטור**. סכום התוצאות אינו קיבולת.
- מדידה מלקוח חיצוני מוגבלת ברוחב הפס של הלקוח — למדוד מ-`127.0.0.1`.
- בקשת טווח מעבר לסוף הקובץ מחזירה מספרים חסרי משמעות.

## התצורה הנוכחית (ולמה)

ב-`/opt/zovex-bot/.env`:
```
STREAM_PARALLEL_PARTS=4      # חלונות במקביל, כל אחד על בוט אחר → מוסיף תפוקה
STREAM_MEDIA_CONNS=4         # חיבורים בתוך בוט אחד → 8 נמדד כגרוע פי 3
STREAM_MEDIA_BANDS_TIMEOUT=6 # היה 3 — חתך בוטים בריאים מוקדם מדי
STREAM_MEDIA_BANDS_PER_MB=3  # היה 2 — תקציב של 5ש' למגה, הדוק מדי
STREAM_EDGE_HEAD=33554432    # 32MB התחלה שמורה בדיסק
```
ב-drop-in (ערכים שאינם ב-`.env`):
```
STREAM_BAND_TIMEOUT_LIMIT=3
STREAM_CHOKE_BACKOFF_MAX=300  # היה 1800 — בוט חנוק נעלם ל-30 דקות
```

## נוהל כשמדווחים על תקיעות

1. `python3 concurrency_test.py` — אם יש זמנים מעל 15 שניות, יש בעיה.
2. `curl -s "http://127.0.0.1:8000/stream/tune"` — לוודא שהתצורה כמצופה.
3. `journalctl -u zovex-bot --since "30 min ago" | grep -c "Retrying"` —
   מאות בשעה = בקשות לטלגרם לא חוזרות בזמן.
4. `systemctl restart zovex-bot` — מחזיר לתקינות; **אם זה עוזר, זו
   התדרדרות ולא באג בקוד המשיכה.**
